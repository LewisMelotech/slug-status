# Accounts on a self-hosted instance

Two ways in: a local username and password, or one of the social providers if you have
configured a `SocialApp` for it. Both work side by side — the login page shows the
credential form, and provider buttons appear beneath it only when a provider exists.

## No email is collected

Signup asks for a username and a password, nothing else. Nothing in this codebase sends
mail, there is no self-service password reset, and a self-hosted instance rarely has SMTP,
so requiring an address would only invite made-up ones.

Login is therefore by **username**. (allauth refuses email as a login method when email is
not a signup field, so the two settings move together.) Social accounts still carry
whatever address their provider supplies.

If you later add SMTP and want addresses back, put `"email*"` into `ACCOUNT_SIGNUP_FIELDS`
and add `"email"` to `ACCOUNT_LOGIN_METHODS` in `botc/settings.py`.

## Closing signup

`LOCAL_SIGNUP_ENABLED=False` closes registration without affecting login, so you can
invite people by hand while everyone who already has an account keeps getting in. Create
accounts yourself in the Django admin, then hand each person a reset link (below) so they
choose their own password and you never learn it.

## Resetting a password

There is no "forgot password" form, because a link nobody can receive is a dead end.
Instead an admin generates one:

1. Django admin → **Users** → tick the person
2. Action → **Generate a password reset link** → Go
3. The link appears in the message at the top of the page. Send it to them however you
   normally talk — Discord, usually.

The link is signed with that user's current password hash and last login, so it:

- works **once** — using it changes the password, which invalidates the token
- dies immediately if the password changes by any other route
- expires on its own after `PASSWORD_RESET_TIMEOUT` (three days by default)

A stale or tampered link lands on a page saying so and telling them to ask for another,
rather than a traceback.

If you would rather set the password yourself, the standard Django admin route still
works: **Users** → the person → the "this form" link beside the password field. That gives
you a password you both know, so the reset link is usually the better habit.

## Permissions worth knowing

| Permission | What it allows |
|---|---|
| `scripts.api_write_permission` | Upload and import via the API, set custom ids, and edit a script's custom id from its page |
| `scripts.set_server_status` | Mark a script as live on the Minecraft server, and see the Server page |
| `scripts.download_unsupported_json` | Download the autogenerated JSON variant |

Grant them under the user's **Permissions** in the Django admin. Superusers have all of
them implicitly.
